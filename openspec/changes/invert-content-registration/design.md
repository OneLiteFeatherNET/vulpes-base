# Design

## Context

On `develop`, every content type follows the same pattern: a public sealed interface (`CustomItem`) extends `VulpesKey` and a generated sealed interface (`CustomItems`), a package-private record (`CustomItemImpl`) implements it and holds a `static final Registry` built from the generated `CustomItemEntries.entries()` on class initialization. The generator writes `CustomItemKeys`, `CustomItems` and `CustomItemEntries` into `src/autogenerated/java` of a clone.

## Goals

- Compile and test `vulpes-base` without any generated code.
- Let several content projects coexist in one server.
- Keep registries immutable after start and free of global state, so tests stay independent.

## Decisions

### Content as an explicit object
```java
public interface VulpesContent {
    List<CustomItem> items();
    List<CustomAttribute> attributes();
    List<CustomSound> sounds();
    List<CustomFontSymbol> fontSymbols();
    List<CustomAdvancement> advancements();
    /** Alias key to current key, for deprecated keys of renamed entries. */
    Map<Key, Key> aliases();
}
```
The plugin generates `CygnusContent implements VulpesContent` with an `INSTANCE`, and constant classes (`CygnusItems.IRON_SWORD`) that hold the built entries. The content object returns those constants, so no registry lookup is needed to create them and there is no initialization cycle.

Alternative considered: `ServiceLoader` discovery. Rejected (design document, open question 2): implicit, depends on classpath layout, and hides which content a server runs.

### Bootstrap returns an instance
```java
public final class Vulpes {
    public static VulpesRegistries bootstrap(VulpesContent... contents);
}
public interface VulpesRegistries {
    Registry<CustomItem> items();
    Registry<CustomAttribute> attributes();
    Registry<CustomSound> sounds();
    Registry<CustomFontSymbol> fontSymbols();
    Registry<CustomAdvancement> advancements();
}
```
`bootstrap` merges all contents, fails on duplicate keys (naming both), on aliases that collide with a key or point to no entry, and on missing or cyclic advancement parents (existing `CustomAdvancementGraph`). It returns immutable registries. There is no static holder: the game keeps the instance (or passes it to its services). This keeps `vulpes-base` free of shared mutable state, which also keeps the tests of games and of this library independent of each other.

Alternative considered: a global `Vulpes.registries()` set once by `bootstrap`. Rejected because it brings back order-dependent tests and a "bootstrap before first access" failure mode.

### Aliases
`Registry.get(Key)` of the bootstrapped registries resolves alias keys to the current entry; `keys()` and `values()` list only current entries. The plugin emits `@Deprecated(forRemoval = true)` constants for the alias keys, so the compiler points game code at the new name.

### Public construction
The package-private records stay the implementations; the interfaces gain static factories that validate as the record constructors do today (`CustomItem.of`, `CustomAttribute.of`, `CustomSound.of`, `CustomFontSymbol.of`). `CustomAdvancement` has eleven properties and a parent reference, so it gets a builder: `CustomAdvancement.builder(key).parent(parentKey).title(…)…build()`. The parent is a key; the advancement tree is resolved against the registry, as `AdvancementTabs` does today. `ItemComponentDecoder` becomes the public, documented `ItemComponents.apply(builder, "minecraft:lore", "[…]", …)`, because generated items pass vanilla component JSON straight through.

The interfaces stay `sealed` with their implementation records as only permitted subtypes, so the library keeps control over validation.

### Static accessors removed
`CustomItem.fromKey`, `values`, `registry` (and the same on the other types, plus `CustomAdvancement.roots/children`) relied on the static registries. They are removed; `VulpesRegistries` offers the same operations. `AdvancementTabs.createAll(manager)` becomes `createAll(manager, registries.advancements())`.

### Attributes follow the contract
`CustomAttribute` gains `minimumValue()`, `translationKey()` (nullable) and `synced()`. The factory validates `minimum <= default <= maximum` and finite values.

## Testing (F.I.R.S.T.)

Each test builds its own `VulpesContent` (a small test implementation) and calls `Vulpes.bootstrap`; no test depends on placeholders or on another test. Tests that need Minestom types keep `MinecraftServer.init()` per test class as today. New tests cover: bootstrap of several contents, duplicate keys across contents, alias resolution, alias collisions, missing and cyclic advancement parents, factory validation, `ItemComponents.apply` with lore and enchantments.

## Migration

1. Release `vulpes-base` with this change (major).
2. The plugin's `minestom` template generates against it; the plugin adds the matching `vulpes-base` dependency.
3. Games switch from the generated clone to plugin plus data JAR and replace static lookups by the registries instance.
